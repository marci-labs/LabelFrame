# 作业状态与载荷分离方案（已授权实施，尚未接入）

> 已有隔离原型，尚未接入产品或迁移用户库。2026-10-26 用户有条件接受离线反向迁移后再降级；[Lealone 评估](lealone-evaluation.md)不推荐替换，条件已满足，授权继续实施。发布/部署文档须随产品落地同步，不把设计批准当作已交付。

## 证据与收益边界

入口：`test/LabelFrame.Core.Tests/Jobs/ClaimStagesPerfTests.cs`；本地原始证据位于 `artifacts/split-payload-20261026/`。每轮独立临时库，200 项，文本 210000 字符或二进制 105000 bytes；每种载荷四轮交替原表/分表顺序。仍使用正常 SQLite 打开与逐张事务，不改同步等级、索引集合或 .NET 作业排序，不发送真实打印指令。

原型先用真实队列提交，再在事务内把载荷复制到 `job_payloads`，重建不带载荷的 `job_items`。阶段测量的领取只多一个按主键连接的载荷读取；完成调用真实内部方法。所有项核对身份、顺序与完整载荷，批末核对 Completed 和无剩余领取。

首轮专项四轮累计状态更新：文本原表 291/188/198/188ms，分表 11/11/9/9ms；二进制原表 91/96/95/111ms，分表 8/10/7/9ms。文本分表 COMMIT 约 144～155ms，而二进制分表一轮 COMMIT 790ms、完成 830ms，说明磁盘/宿主波动仍在。局部收益不能外推为完整提交、Worker、HTTP 或真实出纸提速比例。

临时 200 项迁移约文本 573～625ms、二进制 301～332ms；它只测候选 SQL，没有生产备份/磁盘预检，不能当成大历史库升级时间或空间上限。重建会产生额外数据库/WAL 空间，未执行 VACUUM，原型不代表磁盘占用减少。

加入反向迁移核对后的独立复测，文本更新原表 334/259/226/236ms、分表 18/15/20/18ms，二进制原表 97/93/112/91ms、分表 12/9/8/9ms；更新差异仍在。但分表文本 COMMIT 两轮达 1023/709ms，二进制末轮达 1261ms，未得到稳定整批提交提速证据。该轮文本迁移 688～928ms、二进制 325～478ms。全部正反向核对通过，不能删去慢轮只报告快轮。

## 候选结构与不变量

- `jobs` 保持；`job_items` 保留 id、job_id、item_index、status、error_code、error_message、updated_at；载荷表以 item id 为唯一关联保存原文本和可空二进制。
- 载荷必须一项一份；文本/二进制及 NULL/空数组不互换，不丢错误字段或原日期文本。完整查询与领取通过连接回读完整载荷，不返回伪造空载荷。
- 新作业写入状态与载荷必须同一事务；领取/完成仍每张独立提交。挂起、恢复、取消、重打、启动恢复、幂等和顺序不变。
- 不因载荷缺失而静默内连接丢项：产品实现必须检测不一致并报错，禁止把缺载荷项当成已完成或可忽略。原型反向迁移已有双向缺失检查；产品读取的 fail-closed 尚未实现。
- 不更改公共模型、打印 API 或模板格式；但内部 schema 不兼容旧存储代码，需要明确降级流程，不能仅以“API 不变”宣称全兼容。

## 正向迁移方案（未实施）

1. 宿主停止消费/提交后、Worker 启动前独占维护；同库多实例必须有可靠互斥，不能仅依赖某个对象的内存锁。
2. 识别明确 schema 版本，未知未来版本拒绝打开；兼容有/无 command_bytes 的旧库。不能沿用吞掉迁移异常后继续启动的方式。
3. 创建一致性备份并做空间预检，禁止生拷正在写入的 db 而遗漏 WAL。备份是迁移失败兜底，不是带新作业运行后的降级方案。
4. 单事务复制载荷、重建状态表、恢复原约束与索引，核对双向一一对应及全部字段，最后更新版本标识并提交。失败或取消回滚，原库可用；不在事务外先清空旧载荷。
5. 提交后做完整性验证再开放 Worker；重启可识别已完成迁移，不能重复复制或重置任何状态。

这些为实施门槛，不是已通过验收。原型仅验证了提交前抛错回滚和混合载荷/状态/错误/时间的往返保留，尚未覆盖断电、满盘、取消、多进程争用、大历史库及所有旧 schema。

## 降级边界与用户决议

当前 README 与 DEPLOY 的部分部署形态描述为安装旧版/换旧镜像即可回滚；客户端自动升级篇另明确 MSI 不提供自动降级。用户已接受本方案新增数据操作步骤，产品落地时同步明确适用数据库格式边界。

旧代码直接查询 `job_items.zpl/command_bytes`：在瘦表上完整查询抛 SQLite 异常。简单保留 `job_items` 为兼容视图也不可直接替代：实测初始化建索引报 `views may not be indexed`；即便绕过初始化，INSTEAD OF UPDATE 已改底层行但 ExecuteNonQuery 返回的影响行数使既有 SetItemStatusAsync 返回 null。该实验只排除这个简单兼容视图，不宣称证明所有兼容方案不可能。

已确认采用**显式离线反向迁移后再降级程序**：

- 暂停所有宿主实例；用新维护工具把“当前”状态与载荷重新合成旧表，保留迁移后新增作业、幂等键与最新终态，禁止恢复陈旧备份导致已打印项再次待打。
- 反向迁移前验证数据完整性、备份与空间；同事务重建旧表/索引并校验，成功后才允许更换旧程序。失败保持新格式可用，不输出半个旧库。
- 原型已验证完成 200 项之后反向迁移可被现有完整查询读取，另验证混合五种 Item 状态、错误、中文文本、二进制及原日期文本往返一致；不等于生产维护工具已交付。
- 若要求保持直接换旧程序的原有体验，则暂不采用当前分表候选，继续评估兼容成本，不保留伪空载荷列欺骗旧代码，也不通过同步双写大行掩盖性能收益消失。

**授权已确认**：允许交付维护工具和相应部署文档，继续本地产品实现与验证；不操作真实库、不部署、不把恢复陈旧备份作为运行新作业后的降级方式。

## 产品实现验收清单（待执行）

### 实施细化：迁移内核先行

先实现内部迁移器并在独立临时库验证，再接入存储初始化与维护入口。使用 `PRAGMA user_version` 标识旧格式 0 / 分表格式 1；未知版本或不匹配的表结构拒绝迁移。迁移连接不使用连接池，设置 SQLite `locking_mode=EXCLUSIVE` 后获取并提交独占事务，连接持续持有数据库锁；备份和随后转换期间不释放连接。无法获得锁时失败，要求关闭全部使用该库的进程后重试，不终止其他进程。此锁由 SQLite 跨进程协调，不靠路径命名的内存锁，也不提供在线降级。

使用 SQLite 备份 API 生成同目录、唯一命名且不覆盖的完整备份（包含 WAL 中已提交内容），检查备份完整性后才开始转换。磁盘预检按当前逻辑页大小的四倍加 64 MiB 余量保守估算；这是拒绝明显不足的预检而非容量保证，配额/并发占用/实际文件系统故障仍由事务回滚保护。备份不自动删除，失败保留诊断路径；不自动恢复陈旧备份。转换使用临时表、双向 EXCEPT 字段核对和一一对应检查，最后原子交换并写版本；不执行 VACUUM、不改变 synchronous。额外自定义触发器、视图或索引须显式拒绝，避免重建悄悄丢失未识别结构。

先行阶段不改变产品初始化或实际 schema；接线和维护工具完成后再同步部署承诺及发布说明。

- 新库、旧文本库、混合载荷库迁移；重复初始化；迁移中异常/取消/磁盘不足恢复；并发实例互斥。
- 同事务写入、重复 requestId、重复 item id、空作业、缺失/孤立载荷拒绝；所有公开完整查询字段及错误契约不变。
- 领取顺序、无重复/遗漏、挂起/恢复/取消/迟到完成/失败重打/重启恢复；载荷逐字节不变。
- 新格式运行后反向迁移，旧存储代码读取与继续作业；升级/降级往返不得丢失新作业或重放已完成项。
- 小载荷、文本/二进制大载荷、历史积累的 A-B 对照；真实提交与模拟 Worker 完整链路验证；记录迁移时间和额外磁盘峰值。
