# 性能基线（v1 · 2026-08-25 · 开发机 i5-12500H / .NET 10.0.11）

> 测试方法与运行方式见 `scripts/run-perf.ps1`；CI 每周夜间跑（`.github/workflows/nightly-perf.yml`）。
> 本文档记录当轮数据与通过标准，供后续改动对照。

## 一、微基准（BenchmarkDotNet · ShortRun）

打印热路径 = Skia 整版渲染 → 1bpp 位图 → ^GF 编码（文本+条码+二维码三元素标签）。

| 规格 | 整链路单张 | 分配 |
|---|---|---|
| 60×40mm @203dpi | ~0.72 ms | ~990 KB |
| 100×60mm @203dpi | ~1.7 ms | ~2.2 MB |
| 60×40mm @300dpi | ~2.0 ms | ~2.1 MB |
| 100×60mm @300dpi | ~3.4 ms | ~4.9 MB |

**结论**：50 张批量渲染+编码 = 36–170 ms，远低于「提交到出纸 < 1 秒」预算；分配量随面积线性（1bpp 位图 + 中间 SKBitmap），Gen0/1/2 同收（大批量可感知 GC，量级无害）。

## 二、端到端延迟

### WinHost 单张全链路（提交 → 渲染 → 编码 → 入队 → Worker 发送 → 终态）

30 张逐张（60×40mm @203dpi，零耗时传输）：**p50 ≈ 205ms / p99 ≈ 240ms**（通过标准 p99 < 500ms）。

**关键发现：延迟主体是 Worker 空转轮询的 200ms 周期**（提交后最多等一个空转周期才被领走），渲染+编码仅 ~1ms。
- 对「< 1 秒」指标：余量 4 倍，不构成问题；
- 优化机会（如需 < 50ms 响应）：`LabelJobQueue.SubmitAsync` 后用信号量唤醒 Worker（替代 200ms 轮询）；代价是多一条并发路径需验证。**暂不做**——当前场景无需求。

### Server 路由全链路（提交 → 领取 → 回报，TestServer 进程内）

并发 1 / 5 / 20 虚拟设备 × 每设备 20 作业（TestServer 进程内），全部 0 错误：

| 并发设备 | p50 | p95 | 判定 |
|---|---|---|---|
| ≤ 5（典型规模） | ~3ms | < 2s | 通过 |
| 20（压力位） | 3-4ms | 2-3.3s | 通过（阈值 5s） |

**发现（SQLite 单写者特征）**：20 设备并发时每轮 3 个写事务 × 20 = 60 个写事务竞争单写锁，busy_timeout 排队使 p95 尾部 2-3s——**主体延迟不受影响（p50 恒 3-4ms），无错误无丢失**，属可预期特征而非缺陷。优化机会（有需求再做）：提交 / 回报合批（写事务合并）或写队列串行化消除锁竞争。

## 三、稳定性 soak

Server 混合负载（4 设备并发提交/领取/回报 + notify 长轮询 + 日志 + 列表查询）稳态运行：

| 检查项 | 通过标准 | 5 分钟实测 |
|---|---|---|
| 错误数 | = 0 | 0 |
| WAL 文件 | < 10MB（autocheckpoint=1000 页生效） | 有界 ✓ |
| 托管堆首末 | < 1.5× + 10MB 余量 | 稳定 ✓ |
| 吞吐衰减 | （15 分钟 CI 版观察） | — |

**配套修复**：迭代 29 开 WAL 时未配 `wal_autocheckpoint`（SQLite 默认 1000 页其实已启用——本次显式声明并验证），soak 断言防止未来回归。

## 四、遗留优化机会（有需求再做）

1. **Worker 信号量唤醒**（200ms 轮询 → 事件驱动）：单张系统延迟 205ms → ~5ms；
2. **大批量 GC**：50 张以上连打时分配 ~2MB/张，Gen2 收集齐步——可复用 SKBitmap 池（当前量级不必要）；
3. AndroidHost 渲染性能未测（真机验收时用同基准方法）。

## 环境说明

- 数据采自开发机（i5-12500H，单机 TestServer 进程内），CI 夜间数据以 Actions 日志为准；
- Perf/Soak 测试打 `Trait` 标签，日常 `dotnet test` 与 ci.yml **不执行**（避免时长与阈值抖动），显式过滤运行。
