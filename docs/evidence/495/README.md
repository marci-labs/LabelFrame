# 缺陷 #495 验收证据

客户端安装包的两处修复：更新服务的就绪探测不再连接管道（安装、升级不再在应用程序日志里留下「客户端升级请求被拒绝」的警告）；手动卸载也先让运行中的客户端安全退出（正在打印时拒绝卸载，不强杀）。对应 Issue：[#495](https://github.com/marci-labs/LabelFrame/issues/495)。

## 两轮的步骤

每轮是一条轮次链：开机前自检 → 还原基线、开机 → 复制物料、安装运行时 → 客机脚本逐步执行 → 取回安装日志 → 还原、关机。

| 轮次 | 步骤（依次） |
|---|---|
| 卸载轮 | ① 已发布的 1.6.1 包：安装、读事件日志（对照）、没有客户端运行时卸载。② 候选包：安装、读事件日志、没有客户端运行时卸载。③ 重新安装候选包，启动客户端并等它空闲应答，卸载。④ 重新安装，启动客户端，造「正在打印」，卸载；等作业结束后再卸载。⑤ 重新安装，让客户端只监听非回环地址，卸载；手动停掉客户端后再卸载。⑥ 读候选包阶段的事件日志 |
| 升级回归轮 | ① 已发布的 1.6.1 包：安装、读事件日志（对照）、启动客户端。② 升级到候选包，读状态与事件日志。③ 启动客户端。④ 卸载，读事件日志 |

轮次记录里每一行是客机脚本的一行输出，带宿主机侧的时间戳。

## 与引导程序、离线包的等价关系

引导程序（`packaging/bootstrapper/Bundle.wxs`）里的 `ClientMsi` 是不带 `MsiProperty` 的 `MsiPackage`：安装、升级、卸载客户端时，引导程序都调用这同一个 MSI 的同一执行序列，不传任何自定义的安装或卸载参数。本轮实测的静默调用与此一致；引导程序的完整卸载链路没有另外走查。离线包只附带客户端 MSI 供人工安装，没有脚本去卸载它。

## 验收中发现并处理的问题

都不在产品里，是取证过程与断言脚本自身的缺陷；各项都在对应轮次定稿之前改掉。

**一、第一次运行没有造出「正在打印」。** 客机脚本里 `$labels` 与参数 `$Labels` 只差大小写，而 PowerShell 的变量名不分大小写，提交的请求体不合法（400），作业没有提交成功，「正在打印时卸载」那一步实际是在客户端空闲时执行的。同一轮里升级轮的输出还被写成了卸载轮的文件名（升级轮脚本没有给自己起轮次名）。两处改掉后，两轮都从还原后的基线完整重跑，入库的证据全部取自第二次运行。第一次运行的卸载轮证据留作汇总脚本的对照（`summary-controls.txt` 对照三）。

**二、汇总脚本的四处预期与客机输出不符。** 都是汇总脚本写错，不是产品行为的问题：装完之后应只有一个进程（静默安装不启动客户端），不是两个；升级后客户端报告的版本是源码常量 `1.6.1`，不是包版本 `1.6.99`；一处监听计数把「没有监听」也算成一个监听；「作业完成」那一项的匹配在耗时后面多写了一个单位 `s`。最后一处是轮次链跑完之后才发现的，所以 `chain-log.txt` 里卸载轮的自动汇总退出码是 1；改掉后对同一批客机输出重新汇总，25 项全过。

**三、结构断言的条件求值器遇到空条件会崩溃。** 做变异对照时，「把条件清空」这个变异包让断言报的是参数绑定错误，而不是「恒真，应当在卸载子会话跳过」。求值器改为把空条件按恒真处理；入库的断言结果都是用改后的脚本重新生成的。

## 说明

- 应用程序日志里 LabelFrame 来源的条目：对照包安装后是 1 条信息加 2 条警告；候选包全程只有更新服务的「服务已启动 / 已停止」信息，没有来自 LabelFrame 的错误或警告。
- 拒绝卸载时用户看到的是安装器的通用错误对话框，原因写在安装日志里（与升级被拒时一致，不在本轮范围）。静默轮次只核对了退出码与安装日志。
- 候选包未签名，只进了测试机。
