# 迭代 181（#504）：安装包缺陷修复的验收证据

在纯净 Windows 10 测试机上验证 #504 交付的五个缺陷修复（#498、#499、#500、#501、#502）。被测的是本地构建的候选包（版本号 1.6.99，未签名），不是正式发布的包。对应 Issue：[#504](https://github.com/marci-labs/LabelFrame/issues/504)。

**结论**：AC-01～AC-09、AC-11～AC-13 共 12 条在候选包上全部通过，逐项见「验收标准逐条结果」；AC-10（文档与门禁）随合并与回写完成。有一处没有改：从控制面板「程序和功能」卸载时仍然不询问，见「没有改的一处」。

## 轮次

每一轮是一条轮次链：开机前自检（物料摘要与签名、全部走查在本机对替身向导演练、汇总脚本的对照）→ 还原基线、开机 → 复制物料、客机脚本逐条执行 → 取回客机日志 → 还原、关机。`chain-log.txt` 是轮次链的记录。

六轮共 125 项检查全部通过：向导 26、缺运行时对话框 19、服务端 16、重跑 6、数据与升级 18、清除数据 40。

| 轮次 | 步骤（示意） |
|---|---|
| 向导轮（客户端） | ① 提权启动向导，全新安装到完成页，保持勾选「立即打开 LabelFrame」，点「完成」。② 普通方式启动，同上。③ 取消两个勾选后点「完成」，重启看有没有自启。④ `msiexec /x`：答「否」。⑤ `msiexec /x`：答「是」。 |
| 缺运行时对话框轮 | 等名称解析就绪。没有运行时：① 普通方式启动服务端包。② 普通方式启动客户端包。然后装上 .NET 运行时、临时去掉 WebView2 的注册表登记（先导出备份）：③ 普通方式启动客户端包。每次都是：对话框是第一个窗口、网址显示为文字、鼠标点「打开下载页」、看浏览器。结束后恢复登记并核对。 |
| 服务端轮 | ① 普通方式启动向导全新安装。② 静默重跑。③ `msiexec /fa` 修复。④ 普通方式启动，在维护向导里选「修复」。⑤ 普通方式启动，选「删除」，不勾选。⑥ 同上，勾选。⑦ `msiexec /i {code} REMOVE=ALL`，不勾选。⑧ 同上，勾选。⑨ 1.6.0 覆盖升级。⑩ `msiexec /x` 答「是」。 |
| 重跑轮 | ① 静默重跑，期间逐刻探测服务状态与健康端点。② `msiexec /fa` 修复，同样探测。 |
| 数据与升级轮（客户端） | ① 造数据，`msiexec /i {code} REMOVE=ALL` 勾选清除。② 造数据，不勾选。③ 造数据，1.6.0 → 候选版覆盖升级，重启。 |
| 清除数据轮（两个包） | 每条卸载路径各做一遍勾选与不勾选：重跑安装包选「删除」（经询问页，按一次「上一步」回到类型页再进）；`msiexec /i {code} REMOVE=ALL`（询问页在最前，从确认页回询问页一次）。客户端的四条路径卸载前都先通过客户端接口打一个作业。 |
| 卸载入口探查 | 装客户端并造数据，分别从控制面板「程序和功能」（默认登记项两次、把登记的卸载命令改成三种写法各一次）和「设置 → 应用」里点「卸载」，记录系统实际运行了什么、显示了什么。 |

## 没有改的一处

**从控制面板「程序和功能」卸载时不询问，用户数据保留。** 这正是 #499 报告的现象里用户最常走的一条路径，本轮没有改变它，原因是系统层面的：

- 点「卸载」后，先是系统自己的问题「确实要卸载 LabelFrame Client 吗?」；答「是」后 Windows Installer 以基础界面直接卸载，只有「Windows 正在配置 …，请稍候」进度框，安装包的对话框一个都不出现（`entry2-record.txt` 的 `walk-arp-a` 一段，登记项是默认值）。
- 安装包可以改写登记的卸载命令，但系统不按登记的命令执行。把登记的卸载命令改成 `MsiExec.exe /I{code}`、`/I{code} REMOVE=ALL`、`/X{code} /qf` 三种写法后，从「程序和功能」点「卸载」，结果与默认完全一样（`entry2-record.txt` 的 `walk-arp-b`、`walk-arp-c`、`walk-arp-d` 三段）。
- 「设置 → 应用」里的卸载按钮：探针点了之后一分钟内没有观察到卸载进程或窗口，没有得出结论（`walk-arp-s`、`walk-arp-t`、`walk-arp-u`）。

所以文档写明：要清除数据，请重新运行安装包，在向导里选「删除」。#499 的修复范围是维护向导与命令行 `REMOVE=ALL` 两个入口。

## 取证过程本身的问题

都不在产品里，是取证脚本与排期自身的缺陷。每一处都在对应结论给出之前改掉并重测；这里记下哪些记录不能直接用。

**一、候选包换过一次：维护向导里勾选清除，在第一版候选包上什么都没删。** 第一版候选包（下称候选包 A）的服务端轮里，重跑安装包选「删除」并勾选清除后，配置文件与数据目录都还在（那一遍的逐项结论里 S5-b 不通过）。这一处在产品里：清除动作是模拟用户的延迟动作，以普通方式启动安装程序再进维护向导时拿不到管理员权限，ProgramData 与 Program Files 下的文件删不掉，动作却照常「成功」。机器级的清除动作改为不模拟用户后重建（候选包 B），清除数据轮在 B 上重测通过。为了让最终证据都取自同一对包，先前在 A 上取证的四个轮次（向导、缺运行时对话框、服务端、数据与升级）在 B 上重跑了一遍；入库的是重跑的记录（S5-b 通过）。A 的两个包的摘要见 `materials.txt`。

**二、开机后头几分钟下载页打不开或出得慢，是测试机的名称解析还没就绪。** 候选包 A 的缺运行时对话框轮里，开机后约四分钟点「打开下载页」，浏览器显示「无法访问此页面」（`DNS_PROBE_FINISHED_NXDOMAIN`）；一分钟后第二次点，页面完整加载。单独跑的一遍 WebView2 对话框（开机后约三分钟）同样是「无法访问此页面」。候选包 B 的第一遍缺运行时对话框轮里，第一次点之后页面也迟迟没有出来。对话框、按钮与「浏览器带着官方网址启动」都不受影响，但「页面加载出来」的证据不整齐。走查之前加了「等名称解析就绪」一步（重跑时等了 37 秒），并把「等页面加载」的观察窗延长到 40 秒，缺运行时对话框轮重跑；入库的是重跑的记录，两个 .NET 下载页都完整加载。WebView2 对话框的网址不指向网页（见 AC-04 一行），所以那一次浏览器停在空白标签，没有页面可加载。

**三、重跑轮的监视脚本第一版一次样本也没采到。** 用后台作业采样，作业启动太慢，整段重跑期间一个样本都没有。改成在同一进程里采样，重跑轮重新跑了一遍。

**四、WebView2 的注册表键抄错过一位。** 脚本第一版把键的 GUID 写错，缺运行时对话框轮里的 WebView2 步骤作废（对话框根本没出现）。改正后先单独跑了 WebView2 对话框轮，最后并回缺运行时对话框轮。

**五、卸载入口探查做了四遍，前两遍的记录没有留下来。** 两遍轮次用了同一个轮次名，后一遍覆盖了前一遍的证据；其中一遍因走查卡住被中止。第三遍（`entry-record.txt`）得到了默认登记项下的结论，但改写登记项的三次都没生效（按名字没找到登记项，探针白跑）；三种写法的结论来自第四遍（`entry2-record.txt`）。探查过程中还改过三处：「程序和功能」列表里的行用 UI Automation 读不到，改为点进列表、键入产品名来选中；系统对话框的文字用通常的窗口消息读不到，改用辅助功能接口；系统的「确实要卸载吗」对话框不是前台窗口时不响应默认动作，改用指针点击。

**六、汇总脚本被真实证据纠正过十来处。** 状态文件在条目不存在时的写法、几行输出不是 `键=值` 的形式、客户端数据齐全的文件数阈值、WebView2 界面缓存不算必需、清除数据轮的记录名与页面名，等等。每一处修正后都重跑了对应轮次的汇总，并用篡改对照确认改坏的证据仍会被判不通过；对照脚本自己也错过两处（只复制文本记录不复制宿主机日志，对照显示「通过」时其实没跑；一条篡改模式锚定了行首，而记录行前面有时间戳）。篡改对照还查出一条检查只看行里有没有某个片段（WebView2 登记恢复后是否还在），改坏了仍然通过；改成核对两处登记都显示在之后，对照才不通过。

**七、安装日志的自动判定错过两处。** 起初把 `MSI*.log.updater-service.log`（更新服务的明细日志，不是安装日志）也当安装日志判定而报失败；升级场景里旧产品被卸载时停服务两次是正常的。两处判定都限定到正确的日志后重跑。

**八、客户端的打印出图要靠提交作业才有。** 通过客户端接口打「测试页」不会产生打印出图；清除数据轮改为提交一个自带全部元素的打印作业，出图才出现在用户数据目录的 `print` 子目录里（每个作业两个文件）。

**九、复核时排除过一个怀疑，没有改包。** 复核命令行卸载的记录时怀疑：从「确认删除」页按「上一步」回到询问页后，「上一步」会通向维护类型页，在那里选「更改 / 修复」实际执行的仍是卸载。安装日志显示，清除预选标记的动作排在询问页的对话框链之后才执行，整条链里标记都还在，询问页的「上一步」始终不显示（截图 `shots/clear/` 里 `*-remove-all-*-03-ClearData.png` 也没有这个按钮）。

**十、1.6.1 客户端正式包走不到本轮新增的断言。** 它在脚本更靠前的断言（手动卸载时结束运行中的客户端）处就被拒绝——1.6.1 发布在那次修复之前，脚本遇到第一条不符就停。为了看到本轮新增的断言对「修复之前的产品」说什么，用 master 源码（含那次更早的修复、不含本轮修复）构建了一个客户端包：被「LaunchClientOnExit 必须是同步、失败不阻断的 x64『请桌面外壳启动』动作」拒绝（`structure-client.txt`）。
